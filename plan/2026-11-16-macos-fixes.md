# Фиксы после ревью macOS-порта (2026-11-16)

Статус: завершено (все майлстоуны закрыты, проверено пользователем на слух/глаз;
ветка `macos` смержена с `memory-audit`, готовится PR в main форка).
Ветка `macos` (база — `04c7574` v1.0.2 + порт).
Источник — ревью `origin/main..HEAD`; три подтверждённых бага, один из них с
воспроизводимым регрессионным тестом.

## Milestone 1 — `HttpStream`: перемотка вперёд при активном префетче

**Корневая причина.** `src/stream.rs::read` при `pos >= chunk_end` всегда берёт
заранее скачанный кусок `take_ahead(end)` и ставит `chunk_start = end`. При
перемотке вперёд (`seek` только меняет `pos`, кусок не сбрасывается) `pos` может
оказаться за пределами этого куска: `off = pos - chunk_start >= chunk.len()` →
`return Ok(0)`. Для `Read` ноль — это EOF, symphonia/rodio завершают трек.
Сценарий: скраббинг прогресс-бара в момент, когда до конца куска осталось ~64 КБ
(префетч уже запущен), с перемоткой дальше следующего куска.

**Проверка (RED).** Юнит-тест в `src/stream.rs`: локальный `TcpListener` с
поддержкой `Range`/206 и детерминированными байтами; последовательное чтение до
срабатывания префетча; `seek` за пределы префетч-куска; `read` должен вернуть
данные по новой позиции (сейчас вернёт `Ok(0)`).

**Фикс (GREEN).** Использовать `ahead` только для непрерывного перехода границы
(`pos == end`); при `pos > end` сбрасывать `ahead` и качать `fetch_chunk(pos)`.
После `take_ahead` дополнительно проверить, что `pos` попадает в кусок.

**Критерий:** новый тест зелёный; последовательное чтение и seek назад не сломаны.

## Milestone 2 — `win::pick_folder`: диалог молча не открывается

**Корневая причина.** `src/win/unix.rs::pick_folder` всегда подставляет
`default location (POSIX file "<start>")`. AppleScript коэрсит его в `alias`, а для
несуществующего пути падает (`-1700 Can't make file … into type alias`, проверено).
`start` по умолчанию — `~/Music/Яндекс Музыка`, создаётся только при первом
скачивании. Итог: на свежей установке пункт «Папка для скачивания» ничего не делает
(обработчик при `None` молча выходит).

**Проверка (RED→GREEN).** Вынести построение AppleScript в
`fn choose_folder_script(title, start)`; тест: для несуществующего пути строки
`default location` нет, для существующего (temp dir) — есть. Сначала тест на
текущем поведении (helper всегда подставляет) падает, затем добавляем `.exists()`.

**Критерий:** оба теста зелёные; на свежей установке диалог открывается.

## Milestone 3 — `player.rs::replay`: блокирующий HTTP при повторе

**Корневая причина.** Повтор (`Repeat::One`) вызывает `api.reopen_stream()` —
блокирующий запрос первого куска — прямо в потоке аудиодвижка при пустом sink.
Раньше повтор шёл из кэшированных байт мгновенно; после перехода на стриминг —
слышимый разрыв ~0.3–0.5 с.

**Фикс.** Открывать поток по уже известному `current_url` в фоновом потоке и
присылать `Msg::Audio` (как обычная загрузка). `current_url` не сбрасывать.
Тестом не покрывается (звук/потоки — по AGENTS только ручная проверка).

**Критерий:** повтор не блокирует движок; трек повторяется (ручная проверка).

## Milestone 5 — щелчки и артефакты при перемотке (третья итерация, финальная)

**Корневая причина (полная).** rodio 0.20 жёстко использует `SeekMode::Accurate`
(единственный вызов в `decoder/symphonia.rs`, настройки нет). В symphonia 0.5.5
MP3-demuxer в Accurate-режиме **не прыгает к цели**: `preseek_accurate` для
перемотки вперёд не делает ничего, а дальше парсится **каждый MPEG-кадр от
текущей позиции до целевой** (назад — от начала файла). Каждый кадр: чтение
заголовка + `ignore_bytes(frame_size)`, который seek'ом перепрыгивает тело и
дочитывает ring-буфер — реальные чтения по всему промежутку. Всё это происходит
в аудиоколбэке (`Sink::try_seek` применяется там), и каждое пересечение границы
куска `HttpStream` делает блокирующий HTTPS-запрос → underrun (щелчки) и секунды
ожидания. Этим объясняются провалы всех прошлых подходов: прямой seek — сеть в
аудиопотоке; подмена источника (`Msg::Seeked`) — новый декодер сканировал от 0 до
цели и качал почти весь файл («супер-медленно»), жёсткая склейка давала щелчок;
prime целевого куска — Accurate-скан всё равно читал весь промежуток мимо кэша.

**Возможность библиотеки.** В rodio 0.22.2 есть `DecoderBuilder::with_coarse_seek(true)`
→ `SeekMode::Coarse`: `preseek_coarse` прыгает сразу к линейной оценке байтовой
позиции, ресинхронизация + пара кадров — O(1) чтений около цели. Бонусом 0.22
делает `decoder.reset()` при seek (защита от артефактов MP3 bit-reservoir).
symphonia остаётся 0.5.5.

**Фикс.**
1. rodio 0.20 → 0.22.2 (миграция: `DeviceSinkBuilder::open_default_sink`,
   `Player::connect_new(mixer)` (алиас `Player as Sink`), f32 без
   `convert_samples`, `current_span_len`/`ChannelCount`/`SampleRate` в Eq).
2. `play_loaded`: `Decoder::builder().with_data(stream).with_byte_len(len)
   .with_coarse_seek(true)` — byte_len нужен и для точной длительности MP3.
3. `Cmd::Seek`: движок (не аудиопоток) заранее качает кусок около цели
   (`Shared::prime` с запасом ±8 КБ: coarse приземляется на ~2.9 КБ раньше
   оценки). Уже в памяти — мгновенно. Затем `sink.try_seek` — в аудиоколбэке
   только чтения из памяти.
4. `src/fade.rs`: микро-фейд 10 мс на стыке (затухание → seek при нулевом
   усилении → нарастание) против щелчка от разрыва волны. Библиотечные
   fadein/fadeout не умеют срабатывать по seek, поэтому обёртка `SeekFade`
   с общим `FadeState` (движок ждёт тишины ≤60 мс, источник сам нарастает
   после успешного seek; неудачный seek восстанавливает unity gain).
5. Попутно найден и исправлен баг rewrite'а `HttpStream`: `ensure_chunk`
   проверял primed-слот только при `pos == cend`/`pos < cstart`, перемотка
   вперёд за текущий кусок шла мимо него в сеть.
6. Прыжок UI при перемотке: на отпускании ползунка `drag-progress = -1`, и
   `shown` возвращался к старой `App.position` до применения seek (15–300 мс)
   → отскок назад и прыжок вперёд. Фикс: `Cmd::Seek` сразу пишет
   `sh().position = pos` и шлёт notify — UI (и «Сейчас играет», и текст песни)
   показывают цель мгновенно; sync() после seek подтверждает её из get_pos().
7. Холодная перемотка ускорена: prime-кусок 128 КБ вместо 256 КБ (PRIME) —
   ждать сеть вдвое меньше, дальше обычный префетч продолжает докачку.
   Оригинал почти моментальный, т.к. буферизует трек целиком; у нас стриминг
   ради памяти (~65 МБ). Полная буферизация — отдельное решение с трейдоффом
   по памяти, не делалась.
8. «Моргание» заполнения при перемотке: на отпускании ползунка Slint сбрасывал
   `drag-progress = -1`, и заполнение возвращалось к старой позиции до прихода
   цели из движка; при частых кликах sync() каждой очереди писала свою цель —
   несколько откатов подряд. Фикс: `App.position` стал in-out, и UI ставит цель
   в тот же кадр отпускания (wave.slint, playerbar.slint); движок держит
   `seek_pending` в sync(), пока seek не применён, и отбрасывает устаревшие
   запросы по `latest_seek` (атомик в обёртке Player, пишется в send()).
   Проверено вживую: одиночные и серии кликов применяются, откатов в логе нет.
9. Клики через пару секунд после серии seek: лог показал `read-fetch 187ms` —
   блокирующий HTTP в аудиоколбэке (буфер устройства 50 мс → underrun).
   Причина: после перемотки `ahead` (префетч старого региона) оставался Some,
   `maybe_start_ahead` не стартовал докачку нового региона, и на границе
   primed-куска `fetch_chunk` шёл в аудиопотоке. Фикс: `HttpStream::seek`
   сбрасывает `ahead` при реальной смене позиции. Регрессионный тест
   `seek_invalidates_stale_prefetch` (RED: префетч заблокирован, 3 запроса
   вместо 4; GREEN после фикса). Живой прогон серии кликов: ноль сетевых
   чтений в аудиопотоке; пользователь подтвердил отсутствие кликов на слух.

**Проверка.** Регрессионный тест `coarse_seek_does_not_stream_the_gap`:
синтетический MP3 (4000 тихих MPEG1-кадров, ~105 с) на локальном Range-сервере;
coarse seek вперёд и назад после prime не делает ни одного запроса. Чувствительность
проверена: с `with_coarse_seek(false)` тест падает (8 запросов вместо 2 —
Accurate качает промежуток). Тесты фейда: монотонная огибающая, тишина до seek,
восстановление после неудачного seek. Сам звук — ручная проверка (по AGENTS).

## Milestone 7 — отступ «светофора»

Замер захватом: Finder macOS 26 — центры кнопок (26,26), (49,26), (72,26) pt,
кнопки 14×14; у нас дефолт AppKit (~16,16) — с радиусом 24pt смотрится зажато.
Фикс в `src/mac.rs`: `place_traffic_lights` ставит `standardWindowButton:`
через `setFrameOrigin:` по центрам Finder (y от низа titlebar-контейнера,
его верх совпадает с верхом окна). Нюансы, найденные экспериментом:
кнопки создаются AppKit позже нашей первичной стилизации (retry до появления),
а AppKit сбрасывает frame в своём лейауте — постановка идёт отложенно
(performSelector на main run loop) после resize/becomeKey/exitFullScreen
и первично с задержкой; resize/becomeKey ловятся notification-observer'ом.
Проверка: центры совпадают с Finder попиксельно, в т.ч. после resize окна;
release-бандл замерен тем же способом.

**Исследование «более надёжного способа» (по вопросу пользователя).** На macOS 26
публичного декларативного API для inset'а светофора нет, проверено экспериментом:
- настоящие NSLayoutConstraint + `translatesAutoresizingMaskIntoConstraints=NO`: AppKit
  сам ре-пинит frame кнопок на каждом лейауте (y за пределами контейнера) →
  кнопки клиппятся и исчезают;
- `NSTitlebarAccessoryViewController` (leading): кнопки исчезают совсем;
- приватных сеттеров inset у NSWindow/NSTitlebarView нет (дамп method list;
  есть только `_setCornerRadius:`, который используем для радиуса).
Индустрия (Electron windowButtonPosition, Tauri/tao trafficLightPosition →
`inset_traffic_lights`, readest) — все в итоге делают `setFrameOrigin:` +
повторную постановку на событиях; это и есть наш механизм.

**Live resize.** Во время drag'а AppKit сбрасывает кнопки на каждое mouse-move;
таймеры (default mode) в event tracking mode не срабатывают, а `performSelector:
inModes:` с псевдо-mode NSRunLoopCommonModes empirically не срабатывает вовсе.
Итог: resize-observer ставит кнопки **синхронно** (уведомление приходит после
лейаута AppKit в том же обороте; частота resize-событий = естественный троттл),
becomeKey — отложенно (default + NSEventTrackingRunLoopMode таймеры), создание
кнопок — retry. Проверка: серия из 6 кадров во время drag'а + кадр после —
везде центры Finder, без мигания углом.

## Surprises & Discoveries

- Подтверждено экспериментом: `POSIX file "<несуществующий>" as alias` → `-1700`,
  поэтому `default location` ломает весь `choose folder`, а не игнорируется.
- Главная находка M5: `SeekMode::Accurate` в symphonia 0.5.5 для MP3 — это
  покадровый скан всего промежутка (с реальными чтениями через `ignore_bytes`),
  а не «точный прыжок». Поэтому prime одного целевого куска не помогал, а
  подмена декодера качала файл от начала до цели. Coarse — прыжок за O(1).
- В rodio 0.22 `Decoder` отдаёт f32 сразу; `Sink` → `Player`,
  `OutputStream` → `MixerDeviceSink`; `with_byte_len` включает seekable и
  нужен для длительности MP3 без Xing.
- Радиусы нативных окон macOS 26 разные: Finder ~24pt, TextEdit ~16pt.
  Эталон по просьбе пользователя — Finder.

## Decision Log

- Для M1 тест поднимает локальный HTTP-сервер на 127.0.0.1 (без внешней сети):
  так проверяется реальный путь `open`/`read`/`seek`, а не только чистая логика.
- Для M2 AppleScript вынесен в чистую функцию — единственный способ покрыть
  GUI-зависимый код без открытия диалога.
- Для M3 выбран `reopen_stream(current_url)` в фоне, а не `start_current()`:
  последний заново ищет ссылку (2 запроса) и обнуляет `current_url`.
- Тест-модули держим в конце файлов (clippy `items_after_test_module`).
- M5: вместо самописного symphonia-декодера или патча rodio выбран апгрейд
  rodio 0.20 → 0.22.2 — `with_coarse_seek` есть в стабильной версии, symphonia
  не меняется (0.5.5), миграция компактная. Prime оставлен: coarse читает пару
  кадров вокруг цели, и они не должны ходить в сеть в аудиоколбэке.
- M5: фейд — своя обёртка `SeekFade` (родные fadein/fadeout не срабатывают по
  seek): движок гасит волну до нуля, ждёт ≤60 мс, шлёт seek; нарастание делает
  сама обёртка в `try_seek`. На паузе фейд-аут пропускается (стык не слышен).
- M5: регрессионный тест строит синтетический MP3 из тихих кадров (валидный
  заголовок MPEG1 L3 + нулевые данные) — реальный путь demuxer/декодера без
  внешних фикстур и сети.

## Outcomes & Retrospective

- M1 и M2 закрыты регрессионными тестами (red→green проверено вживую).
- M3 не покрыт юнит-тестом: звук и потоки по AGENTS проверяются вручную.
- M5: две итерации (подмена источника, prime при Accurate) не работали, потому
  что корневая причина была найдена не полностью — скан промежутка в Accurate.
  Третья итерация опирается на возможность библиотеки (coarse seek) и закрыта
  регрессионным тестом с проверкой чувствительности.
- Клики после серии seek: устаревший `ahead` блокировал префетч нового региона;
  закрыто сбросом `ahead` в `HttpStream::seek` + регрессионный тест.
- Светофор: inset как у Finder (26pt), live resize без мигания (синхронная
  постановка в resize-observer); альтернативы (constraints, accessory)
  экспериментально отвергнуты — на macOS 26 AppKit не отдаёт кнопки наружу.
- Мерж `memory-audit` (M3–M9 + CI macOS): единственный конфликт в `sync()`
  (наш `seek_pending` + их `queue_ver`) разрешён объединением; clippy/test
  зелёные (22 теста). Замер RSS на macOS: лендинг idle 532 МБ до мержа →
  193 МБ после; страница альбома при playback 184 МБ. Финальный перемер по
  сценарию README на Windows — шаг пользователя по плану памяти.
- Осталось: ручная проверка повтора (Repeat::One) и диалога «Папка для
  скачивания» на собранном бандле; Windows-прогон CI после пуша PR.
- Светофор, финальный вид (f6b9cc0): радиус 24pt + ручной inset Finder (26,26)
  через setFrameOrigin + convertPoint:fromView:nil; шапки страниц сдвинуты
  целиком на `App.chrome-top` (24px на macOS, 0 иначе) в хосте app.slint,
  верхние градиенты растянуты вверх — внутренняя вёрстка страниц не тронута.
  Радиус 10pt пробовали и отвергли визуально («квадратное» окно). На старте
  финальный лейаут AppKit сбрасывал frame кнопок после нашей постановки —
  закрыто повтором на windowDidBecomeKey/Main и отложенным placeNow через 0.6 с.
  В мини-плеере кнопки скрыты (флаг MINI читает place_traffic_lights).
- Плеер (16cd22f): кнопка play/pause сбрасывалась в play на время загрузки
  следующего трека (`loaded=false` в advance). Корень: sync() выводил playing
  только из loaded; флаг loading означает «идёт переход, играем дальше».
  Предикат playing_flag вынесен и закрыт тестами (red→green).
- Настройки (bf184ed): описание GPU простым языком («Видеокарта рисует интерфейс
  вместо процессора…»), без Metal/DX12.
- Наблюдение (отдельная задача): при запуске из shell через launchctl asuser
  окно иногда остаётся скрытым (NSWindow isVisible=true, но CGWindowList
  onscreen=false); повторный open (reopen → Event::Show → reveal) показывает.
